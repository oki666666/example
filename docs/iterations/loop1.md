# Loop 1: MVP実装と自己批判

## STEP1 問題定義

### 誰のどんな課題を解決するか
- 対象: 締切付きタスクを同時に抱える個人ワーカー/学生
- 課題:
  - 期限と優先度を同時に見渡しづらい
  - 汎用Todoでは「今危険なタスク」が目立たない

### 既存代替手段
- メモ帳、スプレッドシート、既存Todo
- いずれも軽量だが、締切リスク把握に最適化されていない

### なぜ今作る意味があるか
- 小規模でも締切リスク可視化は日次作業の意思決定に直結する
- 個人利用ならSQLite+軽量APIでも価値検証が可能

## STEP2 MVP設計（実装内容）

## 機能一覧（MVP）
1. タスクCRUD（タイトル/説明/期限/優先度）
2. 状態管理（todo/doing/done）
3. フィルタ（all/todo/doing/done/overdue）
4. KPI表示（未完了/本日期限/期限切れ）

## 技術スタックと選定理由
- React + TypeScript + Vite: 画面部品の分離と型安全
- Express + TypeScript: 小規模APIを迅速実装
- Prisma + SQLite: 導入・運用コストが低い
- Zod: API入力バリデーション明確化
- Vitest + Supertest: API回帰テストを軽量に構築

## データモデル（Loop1）
- `Task(id, title, description, status, priority, dueDate, createdAt, updatedAt)`

## UI構造
- ヘッダー
- KPIカード
- タスク追加フォーム
- フィルタ
- タスクリスト（編集ダイアログ付き）

## STEP4 自己評価（自己批判）

## ユーザー視点での問題点
- タスク件数増加時に探しにくい（検索なし）
- 一括処理がなく、運用コストが高い

## 技術的負債
- エラー表示はあるが分類が粗い
- フロントで再取得中心のため体感速度改善余地あり

## スケーラビリティ課題
- 一覧取得が固定ソートのみ
- 検索条件拡張を考慮したAPIになっていない

## UXの弱さ
- キーボード操作やアクセシビリティ配慮が不足
- 削除操作に復元導線がない

## STEP5 改善案設計（次ループ）

### 何を削るか
- なし（MVP機能は維持）

### 何を足すか
- 検索、ソート、一括操作、アーカイブ

### 設計変更
- `archivedAt` 導入によるソフトアーカイブ
- list APIにクエリパラメータを追加

### 技術変更の是非
- 技術スタックは据え置き（現時点で過不足なし）

## STEP6 次ループ方針
- 運用効率を優先改善し、件数増加時の使い勝手を強化する

## 改善前後・判断理由・トレードオフ（Loop1→Loop2）
- 改善前: 単体操作中心で大量タスクに弱い
- 改善後（予定）: 検索/ソート/一括処理で日次処理時間を削減
- 判断理由: 実務では入力より「探す・片付ける」がボトルネック
- トレードオフ: API・UI状態管理が複雑化する
