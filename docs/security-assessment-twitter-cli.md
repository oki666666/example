# twitter-cli 安全性メモ（2026-03-09）

## 結論
- **「本番アカウントでそのまま使う」のは非推奨**（安全とは言い切れない）。
- とくに「逆向きした非公式API」で**投稿/いいね/返信など書き込み系**を実行するCLIは、  
  技術的リスクとアカウント運用リスクの両方が高い。

## 主なリスク
1. **アカウント停止・制限リスク**
   - 非公開/未文書化エンドポイントの利用は、検知や仕様変更で突然失敗しやすい。
2. **認証情報漏えいリスク**
   - Cookie・セッショントークン・Bearer等をCLIに渡す実装だと、ログ・設定ファイル・履歴に残る可能性。
3. **サプライチェーンリスク**
   - npm/pip経由の依存やポストインストール処理に悪性コードが混入する可能性。
4. **権限過多リスク**
   - 書き込み権限を持つトークンで実行すると、誤操作時の影響が大きい。

## 使う前の最低チェック（必須）
- ソースを確認し、**送信先ドメイン**が `x.com` / `twitter.com` / `api.x.com` など想定範囲のみか確認。
- 認証情報の保存場所を確認（平文保存しない、履歴に残さない）。
- `package-lock`/`pnpm-lock` など lockfile と依存元を確認。
- 実行時に不要な書き込み権限を与えない（read-only優先）。
- **捨てアカウントで隔離検証**してから本番適用。

## 運用ガードレール（推奨）
- 本番アカウントでは使わず、検証専用アカウントを用意。
- トークンは短命化し、漏えい時に即失効できるようにする。
- 実行環境を分離（専用コンテナ/VM）し、シェル履歴・ログを定期削除。
- 仕様変更に備え、失敗時の自動再試行や大量実行を抑制。

## ひとことで
- **読むだけ用途**なら比較的低リスクだが、  
  **書き込み用途（投稿/いいね/返信）は高リスク**。  
  「便利」より「アカウント保全」を優先するべき。
